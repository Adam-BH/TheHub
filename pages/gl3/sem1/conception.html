Pourquoi faut-il des principes et des patrons ? Parce qu'un logiciel vit longtemps, grossit et change. Ce chapitre pose le vocabulaire : qualité, cohésion, couplage.

§ 1.1Définitions clés

Génie logicielDomaine des sciences de l'ingénieur qui étudie la conception, la fabrication et la maintenance des systèmes informatiques complexes.
SystèmeEnsemble d'éléments qui interagissent selon des principes et des règles pour réaliser un objectif.
LogicielCode exécutable + bibliothèques associées + documentation.
ModèleReprésentation schématique de la réalité.
Analyse / ConceptionAnalyse = examen de l'existant ; conception = définition de la future application.

§ 1.2Les tâches du génie logiciel

1–2
Spécifier · Concevoir

Besoins, cahier des charges, spécifications ; architecture, modules, interfaces, algorithmes.

3–5
Implanter · Intégrer · Documenter

Codage, assemblage des parties, manuel et aide en ligne.

6–7
Vérifier · Valider

Tests (fonctionnels, fiabilité, sûreté) ; recette, conformité au cahier des charges.

8–9
Déployer · Maintenir

Livraison, installation, formation ; corrections et évolutions.

Pourquoi le génie logiciel

Logiciels volumineux · évolutivité (sinon on recrée au lieu de mettre à jour) · prix · nature dynamique (améliorations continues) · gestion de la qualité.

§ 1.3Qualité d'un logiciel

Critères généraux
  • Opérationnel : budget, utilisabilité, efficacité, exactitude, fiabilité, sécurité.
  • Transitionnel (changement de plateforme) : portabilité, interopérabilité, réutilisation, adaptabilité.
  • Maintenance : maintenabilité, modularité, flexibilité, évolutivité.
Externes (utilisateur) vs internes (développeur)

Externes : fiabilité, robustesse/sûreté, efficacité, convivialité, documentation, ergonomie, sécurité, adéquation, intégrité.

Internes : documenté, lisible, portable, extensible, réutilisable, interopérable, traçable, testable.

8 principes du génie logiciel

Rigueur · Généralisation (généricité, héritage) · Structuration (décomposition en sous-problèmes) · Modularité (modules cohérents, interface indépendante de l'implémentation) · Abstraction · Construction incrémentale · Documentation · Vérification.

§ 1.4Cohésion & couplage

La règle d'or
Bonne conception = cohésion maximale + couplage minimal

Cohésion forte

Les éléments d'un module ont un objectif commun bien défini. Une classe = une responsabilité. Boîte à outils rangée par tiroirs.

Couplage faible

Une classe dépend le moins possible des autres : changer A ne force pas à changer B. Wagons d'un train qu'on ajoute ou retire.

§ 1.5Qu'est-ce qu'un design pattern ?

Définition

Une bonne pratique face à un problème courant : une structure commune et répétitive de composants en interaction (la solution) qui résout un problème récurrent de conception dans un contexte particulier. C'est une capitalisation de l'expérience, partagée sous forme conceptuelle (ce n'est pas du code prêt à l'emploi).

Niveaux : analysis pattern · architectural pattern · design pattern · idiomes (programmation).

Un bon patron
  • résout un problème
  • est un concept éprouvé
  • la solution n'est pas évidente
  • décrit une collaboration entre objets
Le catalogue GoF

Gang of Four : Gamma, Helm, Johnson, Vlissides. 23 patterns en 3 catégories : création (5), structure (7), comportement (11).

CréationComment un objet ou un ensemble d'objets est créé, initialisé, configuré. Abstraire et encapsuler la création.
StructureComment connecter les objets pour que ces connexions résistent aux évolutions. Découpler interface et implémentation.
ComportementInteractions dynamiques entre objets (Observer, Strategy, State… — hors programme du DS).

Cinq principes de Robert C. Martin (« Uncle Bob ») pour obtenir faible couplage et forte cohésion. Pour chacun : la définition, une violation typique et sa correction. Les cinq sont du même format en DS.

§ 2.1Les symptômes d'une mauvaise conception

RigiditéDifficile à changer : un changement en entraîne d'autres. Château de cartes.
FragilitéCasse facilement, souvent à des endroits sans lien apparent. Vase fissuré.
ImmobilitéImpossible de réutiliser un module ailleurs. Meuble collé au mur.
ViscositéFaire « bien » est plus dur que faire un hack. Avancer dans la boue.
OpacitéIllisible, n'exprime pas son intention. Roman aux chapitres mélangés.
Le code spaghetti du cours

FacturationService.java : 2000 lignes qui calculent les prix, appliquent les taxes, génèrent des PDF, envoient des emails, interrogent la base. On ajoute if (client.isFidele()) total *= 0.95;, la facture s'affiche… et le lendemain les PDF ne partent plus. Couplage invisible = fragilité. Argument économique : dans un projet mal conçu, le coût d'un changement croît exponentiellement.

§ 2.2S — Single Responsibility

Définition

« Une classe devrait avoir une et une seule raison de changer. »

// ✗ 3 raisons de changer
class Facture {
  void calculerTotal()    { … } // métier
  void imprimerFacture()  { … } // format
  void sauvegarderEnBase(){ … } // persistance
}
// ✓ une classe par responsabilité
class Facture           { void calculerTotal() { … } }
class FacturePrinter    { void imprimer(Facture f) { … } }
class FactureRepository { void sauvegarder(Facture f) { … } }

Bénéfice : moins de régressions, code plus clair, plus facile à tester.

§ 2.3O — Open / Closed

Définition

« Les entités logicielles doivent être ouvertes à l'extension mais fermées à la modification. » Une multiprise : on ne refait pas le mur pour brancher un appareil.

// ✗ chaque nouvelle forme = modifier la méthode
double calculerArea(Object forme) {
  if (forme instanceof Cercle) { … }
  else if (forme instanceof Carre) { … }
}
// ✓ abstraction + polymorphisme
interface Forme { double calculerArea(); }
class Cercle implements Forme { … }
class Triangle implements Forme { … } // ajout libre
double calculerArea(Forme f) { return f.calculerArea(); }
Signal d'alarme OCP en DS : une chaîne de if … instanceof ou un switch sur un type.

§ 2.4L — Liskov Substitution

Définition

« Les objets doivent pouvoir être remplacés par des instances de leurs sous-types sans altérer la correction du programme. »

class Carre extends Rectangle {
  @Override void setLargeur(int l) { super.setLargeur(l); super.setHauteur(l); } // ✗ effet de bord
}
void agrandir(Rectangle r) { r.setLargeur(r.getLargeur() + 1); }  // sur un Carre, la hauteur change aussi !

Correction : revoir l'héritage (ici, Carre et Rectangle ne devraient pas être en relation d'héritage ; par ex. deux implémentations d'une interface Forme). Bénéfice : on respecte les contrats implicites.

§ 2.5I — Interface Segregation

Définition

« Aucun client ne devrait être forcé de dépendre de méthodes qu'il n'utilise pas. » Menu à la carte plutôt que buffet.

// ✗ interface « grosse »
interface Machine { void imprimer(); void faxer(); void scanner(); }
class ImprimanteAncienne implements Machine {
  public void faxer() { throw new UnsupportedOperationException(); }
}
// ✓ petites interfaces spécifiques
interface Imprimante { void imprimer(); }
interface Faxeuse    { void faxer(); }
interface Scanneuse  { void scanner(); }
class MachineModerne implements Imprimante, Faxeuse, Scanneuse { … }

§ 2.6D — Dependency Inversion

Définition

(A) Les modules de haut niveau ne doivent pas dépendre des modules de bas niveau : les deux dépendent d'abstractions. (B) Les abstractions ne dépendent pas des détails ; les détails dépendent des abstractions. ⇒ dépendre d'interfaces, pas d'implémentations.

// ✗ couplage fort au détail
class ServiceClient {
  private MySQLDatabase db = new MySQLDatabase();
}
// ✓ injection de dépendance
interface Database { void sauvegarder(Object d); }
class ServiceClient {
  private Database db;
  ServiceClient(Database db) { this.db = db; }
}
DIP ≠ « injection de dépendance ». L'injection (passer l'objet par le constructeur) est la technique qui permet de respecter le principe (dépendre d'une abstraction).

Les patrons de création abstraient le new : le client ne sait plus (et n'a plus besoin de savoir) quelle classe concrète est instanciée, ni comment.

Idée commune

Abstraction du processus de création · encapsulation de la logique de création · on ne sait pas à l'avance ce qui sera créé ni comment. Le new partout crée un couplage fort entre le créateur et la classe créée.

Singletoncréation · 1/5
une seule instance
Intention
S'assurer qu'une classe n'a qu'une seule instance et fournir un point d'accès global à celle-ci.
Exemples
Un seul window manager, un seul pilote de périphérique, un seul point d'accès à une base de données (plusieurs instances = surcharge inutile ou comportement incohérent).
Solution
Constructeur privé + attribut statique qui garde l'instance + méthode statique getInstance() qui la crée au premier appel et la retourne ensuite.
public class Singleton {
  private static Singleton INSTANCE = null;
  private Singleton() {}                       // interdit new Singleton() à l'extérieur
  public static Singleton getInstance() {
    if (INSTANCE == null) INSTANCE = new Singleton();   // création paresseuse (lazy)
    return INSTANCE;
  }
}
Version du cours non thread-safe : deux threads peuvent créer deux instances. Solutions : synchronized sur getInstance, ou initialisation directe private static final Singleton INSTANCE = new Singleton();. Bon point bonus en DS.
Factory MethodFabrication · création · 2/5
déléguer l'instanciation aux sous-classes
Intention
Définir une interface de création d'un objet, mais laisser aux sous-classes le choix de la classe à instancier.
Quand
Une classe ne peut pas anticiper la classe des objets qu'elle doit créer ; elle délègue cette responsabilité à ses sous-classes. Ex. framework qui gère plusieurs types de documents.
Participants
Product (interface des objets créés) · ConcreteProduct · Creator (déclare abstract Product factoryMethod(), peut l'utiliser dans ses autres méthodes) · ConcreteCreator (redéfinit factoryMethod pour renvoyer un ConcreteProduct).
Conséquences
Le code ne connaît que Product → marche avec n'importe quel ConcreteProduct ; plus flexible que new direct. Variante : fabrication paramétrée (un paramètre choisit le produit). Creator abstrait ou avec implémentation par défaut.
abstract class Application {                          // Creator
  abstract Document creerDocument();                  // factory method
  void nouveau() { Document d = creerDocument(); d.ouvrir(); }
}
class AppTexte extends Application {                   // ConcreteCreator
  Document creerDocument() { return new DocTexte(); }   // ConcreteProduct
}
Abstract FactoryFabrique abstraite · création · 3/5
familles d'objets
Intention
Fournir une interface pour créer des familles d'objets apparentés sans spécifier leurs classes concrètes.
Exemple
Boîte à outils graphique avec plusieurs look-and-feel (Motif, Presentation Manager) : les widgets ne doivent pas être codés en dur. Une fabrique par apparence crée boutons, fenêtres, menus cohérents entre eux.
Participants
AbstractFactory (opérations createProduitA(), createProduitB()…) · ConcreteFactory (une par famille) · AbstractProduct (une interface par type de produit) · ConcreteProduct · Client (ne connaît que les interfaces).
Collaboration
Normalement une seule fabrique concrète à l'exécution ; changer de famille = changer de fabrique. La fabrique abstraite défère la création à ses sous-classes.
Conséquences
✓ isole les classes concrètes · ✓ échange facile de familles · ✓ cohérence entre produits · ✗ ajouter un nouveau type de produit est difficile (il faut modifier l'interface et toutes les fabriques).
Implémentation
Les fabriques sont souvent des Singletons ; chaque create…() est souvent une Factory Method.
Factory Method vs Abstract Factory : FM = une méthode redéfinie par héritage pour créer un produit. AF = un objet fabrique (composition) qui crée une famille de produits. Question de cours fréquente.
BuilderMonteur · création · 4/5
construction étape par étape
Intention
Séparer la construction d'un objet complexe de sa représentation, pour que le même processus de construction produise des représentations différentes.
Participants
Produit (objet complexe) · Monteur (interface : construire chaque partie) · MonteurConcret (construit les parties, garde l'objet, fournit getResultat()) · Directeur (appelle les étapes dans l'ordre) · le Client crée un monteur, le donne au directeur, lance la construction puis récupère le résultat auprès du monteur.
Exemples
Pizza (Serveur = directeur, MonteurPizzaHawaii) ; convertisseur RTF (RTFReader = directeur, TextConverter = monteur, ASCIIConverter = monteur concret, ASCIIText = produit).
Conséquences
La représentation interne peut varier ; les monteurs sont indépendants (modularité) ; contrôle fin de chaque étape.
abstract class MonteurPizza {                                     // Monteur
  protected Pizza pizza;
  public Pizza getPizza() { return pizza; }
  public void creerNouvellePizza() { pizza = new Pizza(); }
  public abstract void monterPate(); public abstract void monterSauce(); public abstract void monterGarniture();
}
class MonteurPizzaHawaii extends MonteurPizza {                      // MonteurConcret
  public void monterPate()      { pizza.setPate("croisée"); }
  public void monterSauce()     { pizza.setSauce("douce"); }
  public void monterGarniture() { pizza.setGarniture("jambon+ananas"); }
}
class Serveur {                                                       // Directeur
  private MonteurPizza monteur;
  public void setMonteurPizza(MonteurPizza m) { monteur = m; }
  public void construirePizza() { monteur.creerNouvellePizza(); monteur.monterPate(); monteur.monterSauce(); monteur.monterGarniture(); }
  public Pizza getPizza() { return monteur.getPizza(); }
}
Dans le code RTFReader du cours, le switch n'a pas de break : un token CHAR exécuterait aussi convertParagraph(). Ajoute-les si tu le réécris.
Prototypecréation · 5/5
cloner
Intention
Créer de nouveaux objets en dupliquant (clonant) une instance modèle, quand l'objet est coûteux à créer ou que sa classe exacte est inconnue.
Exemple
Logiciel de DAO avec copier-coller : la classe qui gère la copie ne connaît pas la classe exacte de l'élément (cercle, rectangle…) ; elle appelle clone(). Dupliquer est aussi plus rapide qu'instancier.
Participants
Prototype (interface clone()) · ConcretePrototypeA/B (implémentent la duplication) · Client (appelle clone()).
Conséquences
Créer des instances « différentes » sans créer de classes ; attention à la copie superficielle vs profonde (attributs objets partagés ou dupliqués).

Les patrons de structure décrivent comment assembler classes et objets : envelopper, déléguer, composer, partager. Presque tous reposent sur la composition plutôt que l'héritage.

§ 4.0Héritage vs composition

Héritage = boîte blanche
  • Défini statiquement (compilation), réutilisation immédiate.
  • La sous-classe voit l'intérieur du parent et en dépend : l'héritage rompt l'encapsulation.
  • Impossible de changer le code hérité à l'exécution.
Composition = boîte noire
  • Définie dynamiquement (exécution) : l'objet composé contient une référence et délègue.
  • Accès via les interfaces : encapsulation respectée.
  • Un composant peut être remplacé à l'exécution par un autre de même interface.

AdapterAdaptateur · structure · 1/7
convertir une interface
Intention
Convertir l'interface d'une classe en une autre interface attendue par le client, pour faire collaborer des classes aux interfaces incompatibles.
Problème
Réutiliser un « servant » existant dont l'interface n'est pas conforme à celle que les clients appellent.
Participants
Target (interface utilisée par le client) · Client · Adaptee (classe existante à adapter) · Adapter (implémente Target en appelant Adaptee).
2 variantes
Par héritage (adaptateur de classe) : Adapter hérite d'Adaptee et implémente Target. Par composition (adaptateur d'objet) : Adapter contient une référence vers Adaptee et lui délègue.
Usage
Garder plusieurs versions d'une classe quand son contrat change : une classe adaptateur par version, sans modifier les classes utilisatrices.
BridgePont · structure · 2/7
deux hiérarchies indépendantes
Intention
Découpler une abstraction de son implémentation pour que les deux puissent varier indépendamment ; partager une implémentation entre plusieurs objets.
Structure
Programmation par deux interfaces : l'Abstraction contient une référence vers l'Implementor. Ex. MVC (découplage des facettes), représentations interchangeables.
Exemple du cours
abstract class Shape { Color color; Shape(Color c){…} abstract void colorIt(); } avec RedColor, BlueColor… : 3 formes × 3 couleurs = 3 + 3 classes au lieu de 9.
Conséquences
Modularité, indépendance, réutilisation ; chaque côté cache ses détails à l'autre.
Compositestructure · 3/7
arbres partie/tout
Intention
Composer des objets en structures arborescentes (hiérarchies composants/composés) et permettre au client de traiter uniformément objets simples et compositions.
Participants
Component (interface commune, gestion des fils, accès au parent optionnel) · Leaf (feuille, ex. Button) · Composite (stocke les fils, implémente les opérations en les déléguant à ses fils, ex. Container) · Client (n'utilise que Component).
Exemples
AWT/Swing : Component / Container / Button ; expression new Addition(new Nombre(1), new Nombre(3)) ; système de fichiers (répertoire contient fichiers et répertoires).
DecoratorDécorateur · structure · 4/7
ajouter dynamiquement
Intention
Attacher dynamiquement des responsabilités supplémentaires à un objet : alternative flexible à l'héritage pour étendre des fonctionnalités.
Quand
Ajouter des capacités de façon transparente, pouvoir les retirer, quand l'héritage produirait une explosion de sous-classes (combinaisons), ou quand l'héritage est interdit.
Structure
Composant (abstrait) · ComposantConcret · Décorateur (abstrait, hérite de Composant et contient un Composant) · DécorateurConcret (redéfinit la méthode : appelle celle du composant enveloppé puis ajoute son traitement). C'est l'alliance héritage + composition.
public abstract class TexteDecore implements TexteI {
  private TexteI unTexte;
  public TexteDecore(TexteI t) { unTexte = t; }
  public String toHTML() { return unTexte.toHTML(); }
}
public class B extends TexteDecore {
  public B(TexteI t) { super(t); }
  public String toHTML() { return "<B>" + super.toHTML() + "</B>"; }
}
TexteI t = new B(new I(new Texte("Exemple")));   // "<B><I>Exemple</I></B>"

FacadeFaçade · structure · 5/7
une entrée simple

    

      
Intention
Fournir une interface unique, simplifiée pour accéder à l'ensemble des interfaces d'un sous-système complexe.

      
Usage
Interface unique pour un système complexe · séparer un sous-système de ses clients · découper en couches (une façade par point d'entrée de couche) · ex. entrepôts de données.

      
Structure
La façade sait quelles classes du sous-système traitent quelle requête et délègue (avec transformation si besoin) ; nombre de classes du sous-système illimité.

      
Conséquences
✓ simplifie l'usage · ✓ diminue le couplage client/sous-système · ✓ on peut modifier le sous-système sans toucher au client · ne masque pas forcément le sous-système (accès direct possible) · ✗ l'interface unifiée peut être trop restrictive.

    

  

  

    Façade vs Adaptateur
    
Les deux enveloppent des classes existantes qui n'ont pas l'interface voulue. Mais : la façade simplifie une interface (souvent plusieurs classes) sans interface cible imposée et sans polymorphisme ; l'adaptateur convertit vers une interface préexistante (Target), polymorphisme utile.

  


  

    
FlyweightPoids-mouche · structure · 6/7
partager l'état commun

    

      
Intention
Mettre en œuvre efficacement un très grand nombre d'objets de granularité fine en partageant leur état commun au lieu de le stocker dans chaque objet.

      
Clé
État intrinsèque (indépendant du contexte, partagé : couleur + sprite d'une balle, style de trait) vs état extrinsèque (dépend du contexte, passé en paramètre ou gardé à part : position, vitesse, coordonnées).

      
Participants
PoidsMouche (interface qui reçoit l'état extrinsèque) · ConcretePoidsMouche (intrinsèque seulement, partagé) · PoidsMoucheNonPartagé (intrinsèque + extrinsèque) · Fabrique (retourne l'instance existante si elle existe, sinon la crée) · Client (demande à la fabrique).

      
Exemples
Jeu vidéo qui plante faute de RAM (balles, missiles, shrapnels) ; logiciel de DAO (styles de trait partagés, traits avec coordonnées non partagés).

    

  


  

    
Proxystructure · 7/7
représentant

    

      
Intention
Fournir un représentant d'un objet qui en contrôle l'accès : le client parle au proxy, qui offre la même interface et exécute des traitements avant/après l'appel à l'original.

      
Problèmes
Objet distant (RMI, SOAP…) · accès contrôlé (sécurité, autorisations) · objet coûteux à instancier.

      
Participants
AbstractOriginal / Subject (interface commune, le proxy peut remplacer l'original partout) · Original / RealSubject · Proxy (même interface, référence vers l'original) · Client.

      
Types
Cache (résultats fréquents) · Counting (audit, comptage, journalisation avant/après) · Firewall · Protection (droits différents) · Remote (objet distant) · Smart reference (compte de références) · Synchronisation (accès concurrent) · Virtual (création à la demande).

    

  

  
Proxy, Decorator, Adapter ont la même forme (un objet qui en enveloppe un autre). Différence : Adapter change l'interface · Decorator ajoute des responsabilités (et s'empile) · Proxy contrôle l'accès avec la même interface.

Ch2

    
Comment corriger une violation de chaque principe SOLID ?

    

      
SRPExtraire chaque responsabilité dans sa classe (Facture / FacturePrinter / FactureRepository).

      
OCPIntroduire une interface et déplacer le comportement variable dans les sous-classes (polymorphisme).

      
LSPRevoir la hiérarchie : supprimer l'héritage abusif, faire une interface commune plus abstraite.

      
ISPDécouper la grosse interface en interfaces de rôle ; chaque classe implémente seulement les siennes.

      
DIPCréer une interface pour le détail, faire dépendre le haut niveau de l'interface, injecter l'implémentation (constructeur).

    

    
Plusieurs patrons sont des applications directes : Strategy/Decorator → OCP, Adapter → DIP + ISP, Factory → DIP (le client ne fait plus new).

  


  
Bloc BChoisir & modéliser

  

    
Ch3–4

    
Comment choisir le bon patron à partir d'un énoncé ?

    

      
« une seule instance », « point d'accès global »Singleton

      
« les sous-classes décident quel objet créer »Factory Method

      
« familles de produits », « thèmes / look-and-feel », « cohérence entre produits »Abstract Factory

      
« objet complexe construit étape par étape », « même processus, représentations différentes »Builder

      
« copier / dupliquer », « création coûteuse », « classe inconnue »Prototype

      
« interface incompatible », « intégrer une classe existante / une librairie »Adapter

      
« deux dimensions qui varient indépendamment » (forme × couleur, plateforme × fonctionnalité)Bridge

      
« arborescence », « contient des éléments du même type », « traiter pareil simple et composé »Composite

      
« options / suppléments combinables », « ajouter à l'exécution », « explosion de sous-classes »Decorator

      
« simplifier l'accès à un sous-système complexe »Facade

      
« des milliers / millions de petits objets », « mémoire »Flyweight

      
« accès distant / contrôlé / différé / mis en cache », « même interface »Proxy

    

    
Entraîne-toi avec le quiz « Quel patron ? » de l'onglet Synthèse.

  

  

    
Ch3–4

    
Comment dessiner proprement le diagramme de classes d'un patron appliqué ?

    
    
      
  1. Partir de la structure générique du patron (rôles : Target, Adaptee… ou Component, Leaf, Composite…).
    2. 
      
  2. Remplacer chaque rôle par la classe de l'énoncé et noter le rôle en stéréotype ou en commentaire.
    3. 
      
  3. Distinguer interface (<<interface>>, en italique), classe abstraite et classe concrète.
    4. 
      
  4. Bonnes flèches : héritage (trait plein, triangle vide), réalisation (pointillé, triangle vide), agrégation/composition (losange), dépendance (pointillé, flèche).
    5. 
      
  5. Mettre les méthodes clés (celles du patron) et les multiplicités (0..* pour les fils d'un Composite).
    6. 
    

    
Les visionneuses des onglets III et IV montrent la structure générique des 12 patrons : copie la forme, change les noms.

  


  
Bloc CCréation

  

    
Singleton

    
Comment écrire un Singleton correct ?

    
    
      
  1. Attribut private static du type de la classe.
    2. 
      
  2. Constructeur private.
    3. 
      
  3. Méthode public static getInstance() : crée si null, retourne.
    4. 
      
  4. Mentionner le problème multithread et la solution (synchronized ou initialisation statique).
    5. 
    

    
Si le DS demande « une seule fabrique » dans une Abstract Factory, rends la fabrique Singleton : deux patrons combinés = points en plus.

  

  

    
Factory · Abstract Factory

    
Comment savoir s'il faut une Factory Method ou une Abstract Factory, et l'écrire ?

    
    
      
  1. Un type de produit, le choix dépend de la sous-classe → Factory Method (méthode abstraite creerX() dans un Creator).
    2. 
      
  2. Plusieurs types de produits qui doivent aller ensemble → Abstract Factory (une interface avec creerA(), creerB() ; une fabrique concrète par famille).
    3. 
      
  3. Écrire les interfaces produits, puis les produits concrets, puis la ou les fabriques.
    4. 
      
  4. Montrer le client : il ne manipule que des interfaces, la fabrique concrète est choisie une fois (config).
    5. 
    

    
Limite à citer pour Abstract Factory : ajouter un nouveau type de produit oblige à modifier toutes les fabriques (alors qu'ajouter une nouvelle famille est facile).

  

  

    
Builder

    
Comment écrire un Builder (Directeur / Monteur) ?

    
    
      
  1. Produit avec des setters pour chaque partie.
    2. 
      
  2. Monteur abstrait : creerNouveauProduit(), une méthode abstraite par partie, getProduit().
    3. 
      
  3. Monteurs concrets : implémentent les parties.
    4. 
      
  4. Directeur : reçoit un monteur, appelle les étapes dans l'ordre.
    5. 
      
  5. Client : crée le monteur, le passe au directeur, construire(), récupère le produit.
    6. 
    

    
Builder vs Abstract Factory : Builder construit un objet complexe pas à pas et le rend à la fin ; Abstract Factory rend immédiatement des objets d'une famille.

  


  
Bloc DStructure — exercices du cours

  

    
Exercice Adapter

    
« Une application utilise IRépertoire ; intégrer des répertoires manipulés via File »

    
    
      
  1. Target = IRépertoire ; Adaptee = java.io.File ; Client = l'application.
    2. 
      
  2. Choisir la variante : composition (File n'est pas à nous, et on veut pouvoir changer le fichier enveloppé).
    3. 
      
  3. Créer RepertoireAdapter implements IRépertoire avec un attribut File.
    4. 
      
  4. Implémenter chaque méthode de IRépertoire en déléguant à File.
    5. 
    

    
Corrigé proposé (l'énoncé ne donne pas les méthodes de IRépertoire, on en suppose 3)

      
interface IRepertoire { String[] lister(); boolean creer(String nom); boolean supprimer(String nom); }
class RepertoireAdapter implements IRepertoire {
  private final File dossier;                                 // Adaptee (composition)
  RepertoireAdapter(File dossier) { this.dossier = dossier; }
  public String[] lister()       { return dossier.list(); }
  public boolean creer(String n)  { return new File(dossier, n).mkdir(); }
  public boolean supprimer(String n) { return new File(dossier, n).delete(); }
}

    

  

  

    
Exercice DecoratorCh4 · Exemple 3

    
« Distributeur de café : 3 cafés, 4 suppléments, ajout futur facile, afficher le prix »

    
    
      
  1. Composant abstrait Boisson avec getDescription() et abstract double cout().
    2. 
      
  2. Composants concrets : Colombia (1), Expresso (1,2), Deca (0,8).
    3. 
      
  3. Décorateur abstrait Supplement extends Boisson avec un attribut Boisson boisson.
    4. 
      
  4. Décorateurs concrets : cout() = boisson.cout() + prix.
    5. 
      
  5. Client : envelopper — new Caramel(new Chantilly(new Colombia())).
    6. 
    

    
Corrigé complet

      
abstract class Boisson { abstract String getDescription(); abstract double cout(); }
class Expresso extends Boisson { String getDescription(){ return "Expresso"; } double cout(){ return 1.2; } }
class Colombia extends Boisson { String getDescription(){ return "Colombia"; } double cout(){ return 1.0; } }
abstract class Supplement extends Boisson {
  protected Boisson boisson;
  Supplement(Boisson b) { boisson = b; }
}
class Sucre extends Supplement {
  Sucre(Boisson b) { super(b); }
  String getDescription() { return boisson.getDescription() + ", sucre"; }
  double cout() { return boisson.cout() + 0.2; }
}
// Lait (0.2), Caramel (0.4), Chantilly (0.8) : même schéma
Boisson b1 = new Sucre(new Expresso());                       // 1.4 D
Boisson b2 = new Caramel(new Chantilly(new Colombia()));      // 2.2 D
System.out.println(b1.getDescription() + " : " + b1.cout());

      
Sans décorateur : une sous-classe par combinaison (3 cafés × 2⁴ combinaisons de suppléments = 48 classes, et plus encore avec les doubles doses). Avec : 3 + 1 + 4 classes, et un nouveau supplément = une classe (OCP).

    

  

  

    
Exercice Composite

    
« Répertoires et fichiers : nom, droits, effacer, renommer ; parent(), ls(), cd() »

    
    
      
  1. Component : abstract class ElementFS (nom, droits lecture/écriture/exécution, effacer(), renommer(n), référence vers le parent).
    2. 
      
  2. Leaf : Fichier extends ElementFS.
    3. 
      
  3. Composite : Repertoire extends ElementFS avec List<ElementFS> contenu (0..*), parent(), ls(), cd(nom).
    4. 
      
  4. Repertoire.effacer() efface d'abord chaque élément du contenu (récursion), puis lui-même.
    5. 
    

    
Diagrammes de séquence (à dessiner)

      
Effacer un fichier : Client → f : Fichier : effacer() → (f se retire de son parent : parent.retirer(f)) → fin.

      
Effacer un répertoire : Client → r : Repertoire : effacer() → boucle [pour chaque e de contenu] r → e : effacer() (si e est un répertoire, la même séquence se répète récursivement) → puis r → parent : retirer(r).

    

    
C'est la récursion qui montre que tu as compris Composite : l'opération du composite = délégation à tous ses fils + son propre traitement.

  

  

    
Flyweight

    
Comment appliquer Poids-mouche à un énoncé ?

    
    
      
  1. Lister les attributs de l'objet nombreux.
    2. 
      
  2. Séparer intrinsèques (identiques pour beaucoup d'objets : couleur, sprite, style) et extrinsèques (propres à chaque objet : position, vitesse, coordonnées).
    3. 
      
  3. Classe partagée = intrinsèques ; contexte = extrinsèques + référence vers le partagé.
    4. 
      
  4. Fabrique avec une table (Map) : retourne l'instance existante pour une clé, sinon la crée.
    5. 
      
  5. Calculer le gain mémoire (n objets × taille intrinsèque → k styles × taille intrinsèque).
    6. 
    

    
Exemple chiffré à donner : 1 000 000 de balles avec un sprite de 20 Ko → 20 Go ; avec un seul sprite partagé → 20 Ko + 1 000 000 × (petit contexte).

  

  

    
Comparaisons

    
Comment comparer deux patrons qui se ressemblent ?

    

      
Adapter vs FacadeAdapter convertit vers une interface existante (Target) ; Facade simplifie un sous-système, sans interface imposée.

      
Adapter vs Decorator vs ProxyTous enveloppent. Adapter change l'interface ; Decorator garde l'interface et ajoute (empilable) ; Proxy garde l'interface et contrôle l'accès.

      
Bridge vs AdapterBridge est prévu dès la conception (deux hiérarchies) ; Adapter après coup (classes existantes incompatibles).

      
Composite vs DecoratorComposite : un nœud a plusieurs fils (arbre) ; Decorator : enveloppe un seul composant (chaîne).

      
Factory Method vs Abstract FactoryMéthode héritée pour un produit vs objet fabrique pour une famille.

      
Prototype vs FactoryPrototype crée par copie d'une instance ; Factory par instanciation d'une classe.

    

  







  
SOLID dit quoi viser (faible couplage, forte cohésion) ; les patrons disent comment y arriver dans des situations qui reviennent toujours.

S · 2Tableau récapitulatif

  
Une ligne par principe ou patron : ce qu'il dit en une phrase, et quand on le sort.

  

    
Principe / patronEn une phraseUsage (quand / exemple)

    
    
SOLID principes

    
SRPSingle ResponsibilityUne classe n'a qu'une seule raison de changer (une seule responsabilité).Une classe mélange métier, affichage et persistance → la découper (Facture / FacturePDF / FactureRepository).

    
OCPOpen / ClosedOuvert à l'extension, fermé à la modification : on ajoute du code, on ne touche pas l'existant.Un switch / instanceof sur un type → abstraction + une sous-classe par cas.

    
LSPLiskov SubstitutionUne sous-classe doit pouvoir remplacer sa classe mère sans casser le comportement attendu.Une sous-classe lève une exception ou change le contrat (Carré qui hérite de Rectangle) → revoir l'héritage.

    
ISPInterface SegregationPlusieurs petites interfaces spécifiques valent mieux qu'une grosse interface générale.Des classes implémentent des méthodes vides ou UnsupportedOperationException → scinder l'interface.

    
DIPDependency InversionLes modules de haut niveau dépendent d'abstractions, pas de classes concrètes.Un new ClasseConcrete() dans une classe métier → injecter une interface (constructeur / fabrique).

    
Création abstraire le new

    
SingletonGarantit qu'une classe n'a qu'une seule instance et fournit un point d'accès global.Configuration, journal (logger), connexion BD, fabrique unique. Constructeur privé + getInstance() statique.

    
Factory MethodUne méthode de création redéfinie par les sous-classes, qui choisissent quel produit instancier.Le code connaît l'interface Produit mais pas la classe concrète ; un seul type de produit.

    
Abstract FactoryUn objet fabrique qui crée des familles d'objets liés sans nommer leurs classes concrètes.Thèmes d'interface (bouton + fenêtre Windows / Mac), plusieurs produits qui doivent rester cohérents.

    
BuilderConstruit un objet complexe pas à pas ; le même processus donne des représentations différentes.Objet à beaucoup de parties / paramètres optionnels ; Directeur (ordre des étapes) + Monteur (représentation).

    
PrototypeCrée de nouveaux objets en clonant une instance modèle.Création coûteuse ou configuration déjà faite à reproduire ; clone().

    
Structure assembler

    
AdapterConvertit l'interface d'une classe existante en celle qu'attend le client.Intégrer une classe incompatible sans la modifier (exercice IRépertoire / File).

    
BridgeSépare l'abstraction de son implémentation pour que les deux varient indépendamment.Deux dimensions qui se multiplient (Forme × Dessin, Télécommande × Appareil) → éviter l'explosion de sous-classes.

    
CompositeCompose des objets en arbre et traite feuille et groupe de la même manière.Hiérarchies partie-tout : répertoires / fichiers, menus, dessins groupés (exercice répertoires).

    
DecoratorAjoute dynamiquement des responsabilités à un objet en l'enveloppant, sans changer son interface.Options combinables à l'exécution (exercice café + suppléments), flux Java (BufferedReader).

    
FacadeFournit une interface simplifiée unique à un sous-système complexe.Le client n'a besoin que de quelques opérations de haut niveau (ex. HomeTheater.regarderFilm()).

    
FlyweightPartage l'état commun (intrinsèque) entre de nombreux petits objets pour économiser la mémoire.Très grand nombre d'objets similaires (caractères d'un éditeur, arbres d'une carte) ; état extrinsèque passé en paramètre.

    
ProxyUn substitut qui contrôle l'accès à un objet réel, avec la même interface.Chargement paresseux (image lourde), contrôle des droits, objet distant, cache.

    
  


  
S · 3Les ressemblants : différences

  
Les paires qu'on confond au DS : ce qu'elles partagent, ce qui les sépare, et la question qui tranche.

  

    
PairePoint communDifférenceQuestion qui tranche

    
    
Factory Method vs Abstract FactoryCachent la classe concrète créée.FM = une méthode redéfinie par héritage, un produit. AF = un objet fabrique, une famille de produits.Un seul produit ou plusieurs produits qui vont ensemble ?

    
Abstract Factory vs BuilderCréent des objets complexes sans exposer les classes.AF rend immédiatement plusieurs objets d'une famille. Builder construit un seul objet par étapes et le rend à la fin.Plusieurs objets liés, ou un objet assemblé pas à pas ?

    
Prototype vs FactoryCréent des objets sans new côté client.Prototype copie une instance existante ; Factory instancie une classe.On part d'un objet modèle déjà configuré ?

    
Singleton vs FlyweightPartagent des instances.Singleton : une seule instance de la classe. Flyweight : une instance par état intrinsèque, gérée par une fabrique (pool).Une seule instance au total, ou une par valeur partagée ?

    
Adapter vs FacadeEnveloppent du code existant.Adapter convertit vers une interface imposée (Target), souvent une seule classe. Facade simplifie tout un sous-système avec une interface nouvelle.Faut-il respecter une interface déjà attendue par le client ?

    
Adapter vs BridgeDélèguent à un objet « implémentation ».Adapter : après coup, réparer une incompatibilité. Bridge : dès la conception, séparer deux hiérarchies.Les classes existent déjà et ne collent pas ?

    
Decorator vs ProxyMême interface que l'objet enveloppé, délégation.Decorator ajoute des comportements, empilables, choisis par le client. Proxy contrôle l'accès (paresseux, droits, distant), gère souvent lui-même la création du réel.On enrichit le résultat, ou on filtre / retarde l'accès ?

    
Adapter vs DecoratorEnveloppent un objet.Adapter change l'interface ; Decorator la garde et ajoute du comportement.L'interface vue par le client change-t-elle ?

    
Composite vs DecoratorComposition récursive, même interface Composant.Composite : un nœud a plusieurs enfants (arbre), il agrège. Decorator : un seul composant enveloppé (chaîne), il enrichit.Arbre partie-tout ou chaîne d'options ?

    
Facade vs ProxyIntermédiaire entre le client et le reste.Facade : interface différente et plus simple devant plusieurs classes. Proxy : même interface devant un objet.Même interface que l'objet réel ?

    
SRP vs ISP« Petit et ciblé ».SRP parle des classes (une responsabilité). ISP parle des interfaces, vues du client (pas de méthodes inutiles imposées).Le problème est dans l'implémentation ou dans le contrat ?

    
OCP vs DIPPassent par des abstractions.OCP : le but (étendre sans modifier). DIP : le moyen (dépendre d'interfaces, pas de concret).On décrit l'objectif ou la direction des dépendances ?

    
Cohésion vs CouplageCritères de qualité.Cohésion : dans une classe, ses éléments servent un même but (on la veut forte). Couplage : entre classes, leur dépendance (on le veut faible).On regarde l'intérieur d'une classe ou les liens entre classes ?

    
  


  
S · 4Les ponts

  

    
DIP → création
Ne plus faire new Concret() dans le code de haut niveau : les fabriques sont l'outil pour respecter DIP.

    
OCP → Decorator / Composite
Nouveau supplément, nouveau type de nœud : une classe de plus, zéro modification du code existant.

    
Composition > héritage
Adapter (objet), Bridge, Decorator, Proxy, Composite délèguent à un objet contenu : remplaçable à l'exécution, encapsulation respectée.

    
Patrons combinés
Abstract Factory en Singleton, créations via Factory Method ; Flyweight + fabrique ; Composite parcouru par des Decorators.
